# ADR-024: テストを E2E、PBT、Fuzzing、形式手法、単体の 5 層で整備する

- Status: Accepted

## Context

アプリは、記録中のデータの保護、複数の端末の編集権、レストタイマーとプッシュ通知、AI の提案、認証の状態遷移を持つ。
これらの不変条件は、画面の操作だけのテストでは確かめられない。
参照する `../../../brewbook` は、E2E、PBT、Fuzzing、形式手法、単体の 5 種類のテストを持ち、`wrangler dev` と ChromeDriver を使う結合テストと E2E を持つ。
プロジェクトの規約は、TDD、PBT の優先、Fuzzing、モックとスキップの禁止を求める。
テストの層の選び方、PBT と Example-based test の使い分け、Fuzzing の役割、待機と独立性の規則は、`testing-style` が定める。

## Decision

テストを次の 5 層で整備する。
1 つの性質は 1 つの層で確かめる。

| 層 | 確かめるもの | 置き場 | 主な道具 |
| --- | --- | --- | --- |
| 単体 | PBT で表せない固定のシナリオ、エラーパス、境界値 | 各クレートの `tests/` | `cargo test` |
| PBT | 純粋なロジックの不変条件、ラウンドトリップ、単調性 | PBT のクレートの `tests/` | `proptest` |
| Fuzzing | 任意の入力に対するパーサのクラッシュ耐性 | Fuzzing のクレートの `fuzz_targets/` | `cargo-fuzz` |
| 形式手法 | 状態機械の不変条件 | `formal/` | TLA+、TLC |
| E2E | 実物を組み合わせた振る舞い、画面、ブラウザの API | Worker の結合テスト、フロントエンドのブラウザテスト | `wrangler dev`、ChromeDriver、safaridriver、`wasm-bindgen-test` |

### 単体テスト

固定のシナリオ、エラーパス、境界値を確かめる。
PBT で表せる性質は単体テストに書かない。

正常系とエラー経路を対で書く。
エラーは variant の完全一致とエラーコードで固定する。
成功は戻り値の有無だけで終わらせず、保存された値、状態、監査の記録まで固定する。

境界は、仕様から先に列挙してからテストを対応させる。
対象は、RPE の 6、6.5、10、回数の 1、10、11、推定 1RM の 1 回、基礎代謝の下限、たんぱく質の 1.6 と 2.2 g、炭水化物の 0、日本時間の日曜 23:59:59 と月曜 0:00、月末、閏年、ウォームアップとドロップセットのセット数、グリップの組み合わせ、回復状況の 47.9、48、71.9、72 時間である。

時刻、乱数、ID の生成は、純粋なロジックの外から注入する。
テストのために現在時刻を固定できない実装を残さない。

### PBT

`proptest` で、純粋なロジックの性質を確かめる。
1 つのテストに 1 つの性質を置き、shrinking で最小の反例が取れることを確認する。
実行した case の数を数え、case が少なすぎるテストを失敗させる。

対象は次の性質である。

- 推定 1RM は、回数が 1 のとき重量に一致する。
  重量と回数に対して単調で、正の有限の値になる。
  回数が 10 を超えるセットは参考値として扱う。
- 総重量は、ウォームアップを除き、ドロップセットの全段を含め、左右別のセットを合算し、反動の回数を含め、補助の回数を含めない。
  自己ベストの種目別の総重量は、ストリクト回数だけで計算する。
- ストリクト回数は 0 以上で、回数以下である。
- 部位別のセット数は、ウォームアップを 0、通常とドロップセットを 1 と数える。
- 日本時間の日付は、任意の UTC の時刻から一意に決まる。
  `YYYY-MM-DD` の往復が一致し、週は月曜に始まり、月の境界と閏年を跨ぐ場合も日付が一意で正しい。
- 目標カロリーは基礎代謝を下回らない。
  PFC のグラム数は丸めの範囲で目標カロリーに一致し、たんぱく質と脂質の範囲を守り、炭水化物は負にならない。
- CSV は 1 セットにつき 1 行になり、列の対応とセルのエスケープが正しい。
  カンマ、引用符、改行、空セル、日本語を含む固定の期待文字列でも確かめる。
  取り込みはないため、往復はテスト専用のパーサで補助する。
- base64url、CBOR、COSE のエンコードとデコードが往復する。
- 同期の操作は JSON に往復する。
- セッションのトークン、ハッシュの一致、有効期限、Cookie の往復が一致する。
- Web Push の VAPID は、JWT を公開鍵で検証し、ヘッダと payload が一致する。
  aes128gcm は、RFC 8291 のテストベクタで復号して一致する。
- AI の出力の検証は、範囲内の値を受理し、範囲外の値を拒否する。
  痛みやけがの固定の一覧の各語を含むメモでは、負荷を増やす提案を必ず除く。
  一覧の語を含まないメモでは、この除去を理由に提案を落とさない。
- 代わりの種目の候補は、主働筋の重なりが多い順、使う器具が違う順、過去に記録のある順に並ぶ。
  同じ順位の候補は、種目ライブラリの表示順で並ぶ。

PBT が見つけた反例は、Example-based test として残す。
`proptest-regressions` をリポジトリに含める。

### Fuzzing

`cargo-fuzz` で、任意のバイト列と任意のイベント列をパーサに与え、パニックとタイムアウトが起きないことを確かめる。
Fuzzing は「パニックしないこと」だけを担い、性質の検証は PBT に置く。

対象は、WebAuthn の CBOR、COSE、clientDataJSON、attestation object、authenticator data、ID トークンのクレームのパーサ、AI の出力の JSON とテキスト、同期の操作の JSON、CSV のセル、プッシュ通知の payload、Web Push の購読の鍵、Web Push の VAPID JWT と aes128gcm の復号、base64url、ISO 8601 の日時、UUID、時間の解析、RPE の解析である。

corpus はリポジトリに含め、手元の実行で更新する。
実行は nightly の CI で行い、corpus をジョブのキャッシュに保存する。
PR の CI では対象の型検査だけを行う。
見つかったクラッシュは Example-based test に回帰ケースとして加える。

### 形式手法

TLA+ で状態機械を書き、TLC で不変条件を検査する。
TLA+ は抽象の不変条件を担い、E2E は観測可能な振る舞いを担う。
同じ性質を二重に持たない。
仕様は `formal/` に置き、不変条件と要求 ID の対応を `formal/README.md` に記録する。
定数は、端末 2 台、セッション 2 つ、操作 2 つ、タイマー 2 つのように小さくし、TLC が短時間で終わるようにする。

対象は次の 4 つである。

- **編集権と引き継ぎ**: 記録中のトレーニングの編集権、開始した端末、サーバーに保存済みの内容、未同期の変更、引き継ぎ、終了後の同時編集をモデル化する。
  不変条件は、記録中のトレーニングを編集できる端末が常に 1 台以下であること、引き継ぎはサーバーに保存済みの内容からのみ行えること、編集権を持たない端末の書き込みを拒否すること、終了後は同じアカウントのどの端末も編集できること、終了後の同時編集は後勝ちになること、後勝ちの上書き以外では受理済みの書き込みが失われないことである。
  終了後に 2 台で編集する遷移も、TLC の検査に含める。
- **オフライン同期**: 端末内の送信待ちの列、送信、受理、再送、重複、サーバーへの適用をモデル化する。
  不変条件は、同じ操作を複数回適用しても結果が変わらないこと、セットが重複しないこと、受理済みの操作を最終的にサーバーへ適用すること、未同期の変更をサーバーの内容で上書きしないことである。
- **認証**: パスキーのチャレンジ、Google OAuth の状態、セッション、パスキーの追加と削除をモデル化する。
  不変条件は、チャレンジと状態が最大 1 回しか結果を生まないこと、期限切れとログアウトの後のセッションを拒否すること、パスキーを削除しても Google アカウントのログインを失わないことである。
- **レスト通知**: レストの予約、Queue の遅延、取り消し、再予約、古いメッセージ、通知の送信をモデル化する。
  不変条件は、1 つの予約につき通知が最大 1 回であること、取り消した予約は通知しないこと、再予約は最新の終了予定時刻を使うこと、古いメッセージを無視すること、トレーニングの終了後に通知しないこと、終了予定時刻から 30 秒を過ぎたメッセージは送らないことである。

TLC は CI で実行する。
JDK は Temurin 25、`tla2tools.jar` は版と SHA-256 を固定して取得し、リポジトリに含めない。
不変条件が実際に違反を検出することを、ガードを 1 つ外した仕様で確かめ、結果を issue に記録する。

### E2E

実際の Worker、D1、R2、Queues、ブラウザを組み合わせる。
`wrangler dev` でローカルの D1、R2、Queues を起動し、マイグレーションを適用し、Dioxus のビルドを Static Assets として配信する。
D1 のマイグレーションとスキーマの制約は、`wrangler dev` の結合テストで検証する。
ブラウザは Chrome と Safari を `thirtyfour` で操作する。
Chrome は ChromeDriver、Safari は macOS に付属する safaridriver を使う。
`thirtyfour` 以外の追加のクレートは要らない。
パスキーは ChromeDriver の WebAuthn の拡張コマンドで仮想認証器を付ける。
ブラウザの API に依存する部品は、`wasm-bindgen-test` を Chrome と Safari の実ブラウザで実行して確かめる。

ブラウザごとの対象は次のとおりである。

| 対象 | Chrome の E2E | Safari の E2E | staging の実機 |
| --- | --- | --- | --- |
| 画面、API、IndexedDB、Service Worker のキャッシュ | 実行する | 実行する | iOS Safari と Android Chrome でも確認する |
| パスキーの登録とログイン | 仮想認証器で実行する | 対象外 | iOS と PC の Safari、Android Chrome |
| プッシュ通知の配信 | CDP で実行する | 対象外 | iOS と Android、PC Safari |
| オフラインの記録 | CDP で実行する | 対象外 | iOS と PC の Safari、Android Chrome |

Safari の WebDriver は WebAuthn の仮想認証器と CDP を持たない。
そのため、パスキー、プッシュ通知、オフラインのエミュレーションは Chrome の E2E と staging の実機で確かめる。
Safari の E2E は、画面、API、IndexedDB、Service Worker のキャッシュを対象にする。

Google のログインは、テスト専用の OIDC の提供者を別のプロセスで起動して確かめる。
アプリの OAuth のエンドポイントは環境ごとの vars で差し替えられるようにし、テストでは提供者の URL を指す。
テスト専用の提供者は、Google のトークンエンドポイントと UserInfo エンドポイントと同じ形の応答を返す。
本物の Google のアカウントには接続しない。
テスト専用の提供者とテスト用の分岐は、本番のビルドに含めない。

Workers AI の正常系は CI で実行できない。
CI では `wrangler dev --local` で AI の失敗の経路を確かめ、正常系は利用者が staging へデプロイした後に `mise run verify-staging` で確かめる。
AI のプロンプトの組み立てと出力の検証は、PBT と単体テストで確かめる。

プッシュ通知は、ChromeDriver の Chrome DevTools Protocol (CDP) の `ServiceWorker.deliverPushMessage` で、実際の Service Worker に push のイベントを届けて確かめる。
通知の表示、通知を押したときの画面の遷移、購読の登録と解除を確認する。

オフラインの記録は、CDP のネットワークのエミュレーションで通信を切り、IndexedDB への保存、通信を戻した後の再読み込み、復帰後の同期を確かめる。
複数端末の編集権は、2 つのブラウザのプロファイルを起動し、開始した端末だけが編集できること、ほかの端末が閲覧のみになること、引き継ぎの後に元の端末が編集できなくなることを確かめる。

E2E の経路は次のとおりである。

- Google のログイン、初回のアカウントの作成、セッションの Cookie。
- パスキーの登録、ログイン、複数のパスキーの追加と削除、Google からの復旧。
- 空の状態、ルーティン、プログラムからの記録の開始、種目の追加、前回の記録のコピー、セットの入力、ドロップセット、スーパーセット、左右別、時間の種目、RPE、メモ、終了、サマリー、自己ベスト。
- レストタイマーの起動、延長、短縮、スキップ、画面の復帰、プッシュ通知の予約と取り消し。
- スキップとトレーニング終了の後に、予約した通知が届かないこと。
- 終了予定時刻から 30 秒を過ぎた通知が届かないこと。
- オフラインでの記録、通信復帰後の再読み込み、復帰後の同期、未保存の表示。
- 複数端末の編集権の画面表示、引き継ぎの確認、閲覧のみの表示。
- カレンダーで、1 日に複数の部位を行った日の部位別日数とトレーニング日数を確かめる。
- 種目別の履歴とグラフ、部位別の分析、回復状況、種目ライブラリ、ルーティン、プログラム。
- 代わりの種目の候補、並び順、AI を呼ばないこと、ルーティンを変えないこと、その種目を後に回すこと。
- 目標の設定、目標との差の表示、達成が難しい目標を小さい目標に分けて扱うこと。
- AI の失敗時の表示、保存済みの提案の表示と修正と採用、痛みやけがの記述に対する安全ガード。
- CSV の書き出し、1 セット 1 行の列、アカウントの削除による D1 と R2 とパスキーとセッションとプッシュ購読と目標と端末トークンと利用者ごとのレート制限のカウンタの削除。
- ライトとダークの表示、44px と 11px の最小値、角丸と影のない面、スマートフォンと PC の幅。

AI の作り直しが同じ出力を返した場合、最小値に達していない場合に限り不合格とする。
AI の作り直しでは、依頼前後の提案を比較し、重量、セット数、時間の少なくとも 1 つが厳密に小さくなったことと、断定が 1 つ削除または弱められたことを確かめる。
AI-015 の最小値の提案では、「これ以上控えめにできない」と表示されることを確かめる。
同じ端末でログアウトし、再ログインして、記録中のトレーニングを再開できることを確かめる。

Queue の消費の重複、再試行、取り消し、アカウント削除後の扱いを、`wrangler dev` の結合テストで検証する。
代わりの種目の候補が AI を呼ばずに表示されることを、結合テストで確かめる。
目標重量の提案は、達成可能、達成が不可能、時期を設定しないの 3 つの固定シナリオで確かめる。
プッシュ購読の endpoint のホストが許可リストにない場合、400 を返す結合テストを置く。
`http://` の endpoint も 400 になることを確かめる。
許可リストは Safari の `web.push.apple.com` と Chrome の `fcm.googleapis.com` を初期値とする。
IndexedDB のスキーマの移行を、ブラウザのテストで検証する。
レート制限とセキュリティヘッダを、結合テストとブラウザのテストで検証する。
パスキーの `attestation: none` の登録を、仮想認証器の E2E で検証する。

E2E のテストは、実行ごとに一意な利用者を作り、D1 のデータと R2 の接頭辞を分ける。
テストが作った資源は teardown で消す。
待つのは条件であり、固定の sleep を書かない。
サーバーの起動は health の応答、画面は DOM の状態、同期は D1 の行と IndexedDB の状態、通知は Service Worker の状態を条件にする。

### 配置と命名

テストのファイルの置き場と命名は、実装の issue で決める。
テスト名には、検証する対象の名詞か動詞句を使う。
マイルストーンの番号、ユースケースの番号、issue の番号をテスト名に使わない。

### 要求 ID との対応

テストは、守る要求 ID をテスト名か module doc に書く。
テスト名では要求 ID を小文字に正規化し、module doc には PRD の表記で書く。
要求 ID を持たないテストは、その理由を module doc に書く。
issue の `Requirements` に挙げた受入基準ごとに、少なくとも 1 つのテストを対応させる。
受入基準を満たすテストを書けない場合は、テストを省略せず、理由を最終報告に書く。
別のテスト仕様書は作らない。

### CI とローカル実行

`mise run check` で、整形、lint、フロントエンドのビルドと lint、形式手法、単体テスト、PBT、結合テスト、ブラウザのテスト、E2E、Fuzzing の型検査を実行する。
Fuzzing の実行は nightly の CI で行い、`mise run fuzz` に時間の上限を置く。
`mise run verify-staging` は、利用者が staging にデプロイした後に、Workers AI の正常系と実機のプッシュ通知を確かめる。
`verify-staging` は、レスト終了時刻と Service Worker の受信時刻の差を 10 回集計し、5 秒以内が 9 回以上かを判定する。通知が届かなかった試行も失敗として数える。

カバレッジ率を目標にしない。
未カバーの行を、正常系は PBT の strategy の不足、エラーパスは単体テストか Fuzzing の不足、到達不能なコードはデッドコードとして分類する。

同じ失敗に対する修正の試行は 3 回までとする。
待機を含むテストは 10 回以上連続で実行し、安定して通ることを確認する。

## Consequences

編集権、同期、認証、通知の状態遷移を、入力の組合せでは見つけにくい誤りまで検査できる。
一方で、TLA+ の仕様と実装の対応を保つ必要があり、状態を変えるときは仕様も更新する。

E2E は実物の Worker、D1、R2、Queues、ブラウザを起動するため、実行時間が長くなる。
CI の並列化で吸収し、変更に対応するスコープのテストだけを実行する。

テスト専用の OIDC の提供者は、本物の Google の応答の形に合わせる必要がある。
Google の応答が変わった場合は、提供者とテストを同時に更新する。

Workers AI の正常系は CI で実行しないため、モデルの変更や品質の低下を CI では検出できない。
staging の確認と、PRD のプロンプトを使った品質の評価を、モデルを変えるたびに利用者が行う。

Service Worker 自身の wasm は `wasm-bindgen-test` で直接テストしにくい。
プッシュの payload の解析とキャッシュのキーの決定を純粋な関数に分け、E2E の CDP の push でイベントの処理を確かめる。

モックを使わないため、外部の失敗の経路は、実物で起こせる失敗を優先する。
実物で起こせない失敗だけを、別のプロセスの提供者や注入で再現し、何を失敗させたかをテストの doc に書く。
テスト専用のクレートは開発の依存に限り、本番の wasm に含めない。

テストの数が増えるため、テスト名と要求 ID の対応を保つ運用が必要になる。
`mise run check` を CI と手元の共通の入口にし、テストの実行方法を分散させない。
