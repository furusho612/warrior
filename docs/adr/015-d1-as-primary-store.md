# ADR-015: データベースに Cloudflare D1 を使い、直接 SQL で扱う

- Status: Accepted

## Context

アプリのデータは、アカウント、身体情報、種目、トレーニング、セット、ルーティン、プログラム、目標、AI の提案と評価、セッション、パスキー、プッシュ購読である。
これらは互いに関係を持ち、利用者ごとに分離する必要がある。
参照する `../../../brewbook` は D1 を唯一の関係データベースとし、ORM を使わずにプレースホルダ付きの SQL を直接実行している。
D1 は 1 つのデータベースが単一スレッドでクエリを処理し、複数の文を `batch()` で 1 つのトランザクションにまとめる。
有料プランで 10 GB、無料プランで 500 MB の容量を持つ。
D1 のバインディングは wasm 経由の独自 API であり、一般的な ORM は対応していない。

## Decision

本番の関係データベースは Cloudflare D1 とする。
D1 のデータベースは環境ごとに 1 つとし、Worker のバインディングから参照する。

ローカル開発と結合テストでは、`wrangler dev` が提供するローカルの D1 を使う。
本番と同じスキーマと同じコードで動かす。

スキーマの変更は `wrangler` の D1 マイグレーションで管理し、SQL ファイルをリポジトリに含める。
デプロイの前に、対象の環境へマイグレーションを適用する。

SQL は ORM を使わず、プレースホルダ付きの SQL を直接渡す。
SQL の組み立ては純粋なロジックのクレートに置き、D1 への実行は Worker のクレートに置く。
この分離により、SQL の組み立てをネイティブのテストで検証できる。

`users` は利用者自身の行であり、利用者 ID の列を持たない。
利用者に属するテーブルは利用者 ID の列を持ち、すべてのクエリで利用者 ID を条件に含める。
利用者に属さないマスターのテーブルは利用者 ID を持たない。
利用者 ID を持たない行は、マスターの種目、あらかじめ用意したプログラムとその日、筋肉の単位、ログインのチャレンジ、Google OAuth の状態、IP ごとのレート制限のカウンタである。
マスターの種目と独自種目は別の表に置く。
マスターの種目は利用者 ID を持たず、独自種目は利用者 ID を持つ。
ログインのチャレンジと OAuth の状態の行は、認証の前の利用者を持たない。
マスターの種目の編集と削除は、利用者ごとの上書きの表に保存する。
あらかじめ用意したプログラムは全体のマスターとし、独自のプログラムは利用者に属する。利用者が取り込んだルーティンは利用者ごとのルーティンとして保存する。独自のプログラムの日と日のルーティンの参照は、独自のプログラムと同じ利用者に属する。
利用者ごとに、進行中のプログラム、取り込み元のプログラム、次に行う日の位置を持つ。
トレーニングは、開始元の種別と、開始元のルーティン ID またはプログラムの日 ID を任意で持つ。用意したプログラムから開始したトレーニングはプログラムの日 ID、独自のプログラムから開始したトレーニングは独自プログラムの日 ID を持つ。
利用者ごとのレート制限は、利用者ごとの表に置き、利用者 ID を持つ。
IP ごとのレート制限は、IP ごとの表に置き、利用者 ID を持たない。
主キーは UUID v4 の文字列とする。
記録中のトレーニング、トレーニングに追加した種目、セット、ドロップセットの段、スーパーセットの組は、アプリが生成した UUID v4 を使う。
マスターの種目、マスターのプログラム、独自のプログラム、ライブラリで作る独自種目、その他の行は、サーバーが生成した UUID v4 を使う。
サーバーは ID の形式と所有権を検証して保存する。
時刻は ISO 8601 の UTC の文字列で保存する。
トレーニングの日付は、日本時間で決めた `YYYY-MM-DD` の文字列で保存する。
複数の文をまとめて書き込むときは `batch()` を使う。
一覧のページングはカーソル方式とする。

バックアップは D1 の Time Travel に依存し、独自のバックアップを作らない。
AI の入出力のスナップショットと CSV の書き出しは D1 ではなく R2 に置く。
アカウントの削除では、利用者に属するすべての行 (身体情報、目標、トレーニング、セット、種目、種目のお気に入り、設定、ルーティン、独自のプログラムとその日と日のルーティンの参照、プログラムの進行、AI の出力と入力のスナップショットのメタデータ、レスト通知の予約、書き出しのメタデータ、パスキー、セッション、プッシュ購読、端末トークン、利用者ごとのレート制限のカウンタ) と R2 の `users/<利用者 ID>/` と `exports/<利用者 ID>/` のオブジェクトを削除する。

## Consequences

D1 の制約がスキーマとクエリの形を決める。
アプリケーション側で任意の `BEGIN` と `COMMIT` を挟むトランザクションは使えない。
複数の文をまとめる処理は `batch()` の単位で設計する。

1 つのデータベースは単一スレッドで処理する。
個人利用の規模では問題にならないが、書き込みが多い処理は `batch()` でまとめ、クエリの回数を減らす。

Time Travel で復旧できる期間は、無料プランで 7 日、有料プランで 30 日である。
それより前の状態へ戻すための独自のバックアップは持たない。
アカウントの削除は、アプリが保持する行とオブジェクトを削除する操作である。D1 の Time Travel は削除した行も保持期間中は復元できるため、提供者の保持期間を過ぎるまでバックアップからの復元を防げない。削除の確認の画面にこの保持を表示し、アプリの経路では削除後に復元できないことを保証する。

SQL の組み立てを純粋な関数に分けるため、ネイティブのテストと PBT で検証できる。
D1 のバインディングに触る部分は、`wrangler dev` の結合テストで検証する。
マスターと利用者のテーブルを分けるため、クエリは利用者 ID の有無を意識する。
アカウントの削除では、利用者に属する表の一覧を削除の対象として持ち、追加した表を漏らさない。

大きな JSON や CSV を D1 の行に詰めない。
D1 の行の大きさの上限を避け、クエリが大きなデータを走査しないようにする。
