## 目的

PRD の数値の置き場を確認し、機能章と非機能要件の役割をそろえる。
実装サービス名を PRD から除き、要求の言葉だけを残す。

## 優先度根拠

要求の意味は変えないが、数値と実装詳細が各章に散ると、運用値の変更で複数箇所を直すことになる。
リリース前の文書整理として行う。

## 現状

- 0070 が `REQ-TMR-009` の 30 秒と `REQ-AI-009` の 2 〜 10% を、PRD の要求と受入基準に反映する。
- レート制御の初期値は非機能要件の表にある。

- 回復の 48 〜 72 時間、種目の 100 〜 110 種、24 の筋肉の単位は機能章にある。
- メモの 2000 文字と時間の 86400 秒は PRD になく、0033 と 0030 にある。要求を追加するかは未決であり、この issue では扱わない。
- PRD の非機能要件には、保存先を「サーバー」と書く箇所がある。これはマルチデバイス同期の要求であり、実装サービス名ではない。

## 設計方針

0070 の決定を変えない。30 秒と 2 〜 10% は 0070 の置き場のままにする。
レート制御の表と計算ルールの定義を確認し、機能章が数値を再掲している場合は見出しの語で参照する。
2000 文字と 86400 秒は要求の追加になるため、この issue では扱わない。必要なら別 issue を起票する。
実装サービス名 (`D1`、`R2`、`wrangler`、`Workers AI`) は PRD から除く。「サーバー」は要求の言葉として残す。
要求 ID と要求の意味は変えない。

### 置き場の分類

- 非機能要件: レート制御の上限と窓、保持期間、タイムアウト、同時接続などの運用値。
- 計算ルールと用語定義: 推定 1RM、PFC、現在の記録の 7 日間、前回、総重量、セット数の定義。
- 機能章: プログラムの進行の目安 2 〜 10%、回復の 48 〜 72 時間、種目の 100 〜 110 種、24 の筋肉の単位。
- ADR と issue: 保存先のサービス名、テーブル名、API の形、プロンプトの実装。
