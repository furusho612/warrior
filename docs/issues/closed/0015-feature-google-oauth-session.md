# Google OAuth のログインとセッションを実装する

- Requirements: REQ-NFR-006, REQ-NFR-009, REQ-MYP-007
- Priority: High
- Created: 2026-11-12
- Completed: 2026-11-13
- Model: deepseek-v4.1-flash:1017
- Branch: feature/feature-google-oauth-session

## 目的

Google アカウントを本人確認の起点にしたログインと、サーバーが発行するセッションを実装する。
記録をアカウントに紐づけ、同じアカウントでログインした複数の端末から同じ記録を見られるようにする。

## 優先度根拠

すべての利用者向けの画面と API がログインを前提にする。
セッションの形を先に固定しないと、認証の境界と利用者ごとのデータの分離が後から崩れる。

## 現状

0004 の `users` の最小の表と、0006 の HTTP 基盤がある。
しかし、Google の認可コードフロー、セッション、ログアウト、認証済みの利用者を要求する仕組みがない。

## 設計方針

Google のログインは OAuth 2.0 の認可コードフローで行う。
クライアント ID とリダイレクト URI も含め、認可の URL、トークンの URL、UserInfo の URL を環境ごとの vars から読む。
テストでは、0008 のテスト用の OIDC の提供者を指す。

ログインの開始で、32 バイトの乱数の `state`、`nonce`、コード検証子を生成し、D1 に保存する。
有効期限は 5 分とし、使用は 1 回とする。
`state` は HttpOnly、Secure、SameSite=Lax の Cookie にも保存し、コールバックの `state` と一致することを確かめる。
認可の要求では、コード検証子の SHA-256 の base64url を `code_challenge` として送る。

コールバックでは、認可コードをサーバー間の TLS で Google のトークンエンドポイントと交換する。
ID トークンはクライアントから受け取らず、トークンエンドポイントの応答から受け取る。
サーバーは ID トークンの署名を検証しない。
ID トークンの payload をデコードし、`aud`、`iss`、`exp`、`nonce` を検証する。
利用者の情報は UserInfo エンドポイントから取得し、`sub` と `email_verified` を検証する。
ID トークンの `sub` と UserInfo の `sub` が一致することを確かめる。
JWT の署名検証のクレートは追加しない。

初回のログインで `users` の行を作り、Google の `sub` を紐づける。
2 回目以降は同じ `sub` の行を更新する。
表示名とメールアドレスは画面の表示にだけ使う。

ログインの後は、サーバーが発行するセッションで認証する。
セッションは 32 バイトの乱数とし、D1 には SHA-256 のハッシュだけを保存する。
有効期限は発行から 30 日とする。
セッションは HttpOnly、Secure、SameSite=Lax の Cookie で渡す。
アプリは Google のトークンとセッションの秘密を保存しない。

認証済みの利用者を要求する API は、Cookie のセッションをハッシュし、期限切れでない行を引く。
見つからない場合は 401 を返す。
URL の ID が認証中の利用者に属することを検査し、属さない場合は 404 を返して資源の存在を漏らさない。この検査を共通の関数に置き、後続の ID 指定経路はすべてこれを使う。
`GET /api/me` はログイン中の利用者の表示名とメールアドレスを返す。

ログアウトでは、セッションの行を物理削除し、Cookie を消す。
アカウントの削除は 0017 で行う。

ログには、認可コード、ID トークン、アクセストークン、セッションの値を出さない。

## 完了条件

- [ ] ログインの画面から Google のログインを開始でき、認証の後にホームへ移動する。
- [ ] Google アカウントで登録してログインでき、同じアカウントでログインした別の端末から同じ利用者として認証される。これは REQ-NFR-006 の受入基準「Google アカウントで登録してログインできる」「同じアカウントでログインした別の端末からも同じ内容で表示される」のうち、認証の部分を満たす。記録の表示は後続の issue が担う。
- [ ] セッション Cookie が HttpOnly、Secure、SameSite=Lax であり、値は 32 バイトの乱数である。
- [ ] D1 にセッションの値そのものではなく SHA-256 のハッシュだけが保存される。
- [ ] 期限切れのセッションと、ログアウトで削除したセッションを拒否する。これは REQ-NFR-009 の受入基準「別のアカウントでログインした利用者は、身体情報と記録を閲覧できない」を、セッションの境界の側から支える。
- [ ] 共通の所有者検査が、認証中の利用者 ID と資源の利用者 ID が一致しない場合に 404 を返す。単体テストで確かめる。後続の ID 指定経路は、それぞれの完了条件で同じ検査を確かめる。
- [ ] `state` と `nonce` を検証し、`state` の再利用と 5 分を過ぎた `state` を拒否する。
- [ ] ID トークンの `aud`、`iss`、`exp`、`nonce` を検証し、ID トークンと UserInfo の `sub` の一致を確かめる。
- [ ] ID トークンをクライアントから受け取る経路がない。
- [ ] ログアウトでセッションの行が削除され、そのセッションで API を呼ぶと 401 になる。これは REQ-MYP-007 の受入基準「マイページからログアウトでき、ログアウトの後は記録画面を開けない」のうち、ログアウトの部分を満たす。
- [ ] ログに認可コード、ID トークン、アクセストークン、セッションの値が出ない。
- [ ] `CHANGES.md` を作り、`## develop` に `[ADD]` で Google アカウントのログインの追加を書く。担当者行は `@Shoichi` とする。
- [ ] テスト用の OIDC の提供者を使う Chrome と Safari の E2E で、ログイン、ログインの後のホームへの移動、`/api/me`、ログアウト、再ログインを確かめる。
- [ ] 単体テストで、`state` の検証、ID トークンの payload の検証、セッションのハッシュ、Cookie の属性を確かめる。
- [ ] PBT で、任意のセッションの値のハッシュが決定的で、出力の長さが一定であることを確かめる。暗号の性質は `sha2` のテストベクタで確かめる。

## 解決方法

`backend/warrior/src/auth/mod.rs`、`oauth.rs`、`session.rs` を追加する。
`backend/warrior/src/router.rs` に `GET /api/auth/google/start`、`GET /api/auth/google/callback`、`POST /api/auth/logout`、`GET /api/me` を追加する。
`migrations/` に `auth_sessions`、`oauth_states` の表を追加する。`users` の Google の `sub` は 0004 の `google_sub` を使う。
`backend/warrior_core/src/auth.rs` に `state`、`nonce`、コード検証子、セッションのハッシュの純粋な関数を置く。
`backend/warrior/tests/e2e_auth.rs` に E2E を追加する。
`backend/pbt/tests/auth.rs` にセッションのハッシュの性質テストを置く。
`frontend/src/screens/login.rs` に、Google のログインを開始する画面と、認証のエラーの表示を置く。
`frontend/src/text.rs` にログイン、ログアウト、認証エラーのキーを追加する。

## 結果

Google OAuth の認可コードフロー、D1 の state、セッション、`GET /api/me`、ログアウトを実装した。
ログイン画面から認可を開始し、認証の後にホームへ移動する。Chrome の E2E と結合テストで、state の 1 回限りと期限切れ、セッションの期限切れ、複数端末での同一利用者、ハッシュだけの保存、ログアウトを確認した。
ログインの誤りは `/login/error` に表示する。Safari の E2E は CI の macOS ジョブで実行する。
