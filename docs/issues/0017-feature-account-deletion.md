# アカウントの削除と利用者に属するデータの削除を実装する

- Requirements: REQ-MYP-007, REQ-NFR-010
- Priority: Medium
- Created: 2026-11-12
- Model: deepseek-v4.1-flash:1017
- Branch: feature/feature-account-deletion

## 目的

利用者がアカウントを削除したとき、利用者に属するすべてのデータを D1 と R2 から削除する。
削除の後に、古いセッションとパスキーでログインできないようにする。
削除の処理を再実行しても、同じ結果になるようにする。

## 優先度根拠

アカウントの削除は段階 4 の機能であり、記録、AI、パスキー、プッシュ購読が実装された後に作る。
一方で、削除の対象の表の一覧を後から足すと、表の追加のたびに削除の漏れが起きる。

## 現状

0015 でセッション、0016 でパスキー、0055 以降で AI の出力とスナップショット、0036 以降でプッシュ購読を保存する。
しかし、利用者に属する行と R2 のオブジェクトをまとめて削除する処理がない。

## 設計方針

`DELETE /api/account` を追加する。
認証を必須とし、要求の本文に `{"confirm":"delete-account"}` を要求する。
画面の確認は 0063 が担う。
サーバーは、確認の値がない要求を 400 で拒否する。

削除の対象は、利用者に属するすべての行とする。
対象は、利用者の行(`users`)、身体情報、目的、週あたりの日数、活動量、PFC の調整値、トレーニング、種目、セット、ドロップセットの段、スーパーセットの組、メモ、ルーティン、プログラムの進行、目標、AI の出力、AI の入力スナップショットのメタデータ、パスキー、認証セッション、プッシュ購読、端末トークン、利用者ごとのレート制限のカウンタとする。
削除の対象には、端末内の記録、設定、キャッシュ、端末トークンの Cookie も含む。
端末内の削除は、削除の応答を受けた端末で行う。ほかの端末は、次回のログイン時に、削除済みのアカウントの端末内データを破棄する。
R2 の `users/<利用者 ID>/` の接頭辞のオブジェクトも削除する。
マスターの種目とプログラム、筋肉の単位は削除しない。
利用者ごとの上書きは削除する。

削除の順序は、R2 の接頭辞を先に削除し、その後に D1 の行を `batch()` で削除する。
R2 の削除が失敗した場合は D1 の行を削除せず、エラーを返す。
R2 の削除は同じ接頭辞に対して再実行しても同じ結果になる。
D1 の削除が失敗した場合は、セッションが残るため、利用者は同じセッションで再試行できる。
D1 の削除が成功した後は、セッションとパスキーを削除済みであり、古い認証情報ではログインできない。

D1 の削除の対象の表の一覧は、`backend/warrior_core` の 1 つの定数に置く。
`migrations/` の `CREATE TABLE` を読み、すべての表を「利用者に属する」「マスター」「一時」の 3 つに分類する。
利用者に属する表がすべて削除の対象に含まれることを結合テストで確かめる。
`users` と、`set_segments` や `superset_members` のように親から所有される表も、利用者に属する表として扱う。
新しい表を追加する issue は、この分類も更新する。

削除の後、応答でセッションの Cookie を消す。
削除の後に同じ Google アカウントでログインした場合は、新しい `users` の行を作る。
削除の前の記録は残らない。

## 完了条件

- [ ] マイページからアカウントを削除でき、削除の前に記録がすべて消える旨の確認が表示される。これは REQ-MYP-007 の受入基準「アカウントの削除では、削除の前に記録がすべて消える旨の確認を表示し、確認した後に削除を実行する」のうち、サーバーの処理を満たす。確認の画面は 0063 が担う。
- [ ] 削除の後に、身体情報、記録、目標、端末トークン、プッシュ購読、パスキー、セッション、利用者ごとのレート制限のカウンタ、R2 の利用者の領域が残らない。これは REQ-NFR-010 の受入基準に対応する。
- [ ] 端末内の記録、設定、キャッシュ、端末トークンの Cookie が削除され、削除の後に同じアカウントでログインしても復元されない。端末内の削除は 0063 と 0021 が担う。
- [ ] 削除の後に、削除の前に発行したセッションで API を呼ぶと 401 になる。
- [ ] 削除の後に、削除の前に登録したパスキーでログインできない。
- [ ] 削除の後に同じ Google アカウントでログインすると、新しいアカウントが作られ、削除の前の記録がない。
- [ ] `migrations/` のすべての表が「利用者に属する」「マスター」「一時」の 3 つに分類され、利用者に属する表が削除の対象の一覧に含まれる。この issue の完了時点で存在する表を対象とし、後続の issue が表を追加するたびに分類とテストを更新する。
- [ ] 削除の対象に `users` の行が含まれる。
- [ ] サーバーの削除処理を同じ利用者 ID に対して 2 回実行しても、最終状態が同じになる。
- [ ] 公開 API の 2 回目の削除の呼び出しは、セッションが削除済みのため 401 を返す。これは冪等性の条件と分けて確かめる。
- [ ] R2 の接頭辞の削除が失敗した場合、D1 の行を削除せず、エラーを返す。再実行で削除できる。
- [ ] 削除の処理が、マスターの種目、プログラム、筋肉の単位を削除しない。
- [ ] テスト用の OIDC の提供者とローカルの D1、R2 を使う E2E で、すべての表の行と R2 のオブジェクトを作り、削除の後に残らないことを確かめる。
- [ ] 表の一覧の網羅は、`migrations/` の SQL を読む結合テストで確かめる。モックは使わない。
- [ ] 削除の順序と対象の一覧を純粋な関数で表し、単体テストで確かめる。
- [ ] PBT は、削除の対象の一覧の網羅が入力の SQL に依存するため使わない。例示の SQL と結合テストで確かめる。

## 解決方法

`backend/warrior_core/src/account_deletion.rs` に、削除の対象の表の一覧と、R2 の接頭辞を組み立てる関数を置く。
`backend/warrior/src/account.rs` に `DELETE /api/account` を置く。
`backend/warrior/src/router.rs` に経路を追加する。
`frontend/src/screens/mypage.rs` に削除の確認の画面を置く。画面の仕上げは 0063 で行う。
`backend/warrior/tests/e2e_account_deletion.rs` に E2E を追加する。
`frontend/src/storage/` に、アカウント削除の応答を受けた端末で IndexedDB、Cache API、端末トークンの Cookie、設定を削除する処理を追加する。削除済みのアカウントの端末内データは、次回のログイン時に破棄する。
`backend/warrior/tests/account_deletion_tables.rs` に、`migrations/` を読む分類のテストを置く。
