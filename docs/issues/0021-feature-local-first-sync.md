# 端末内への保存と送信待ちの列を実装する

- Requirements: REQ-NFR-003, REQ-NFR-004, REQ-NFR-005, REQ-NFR-007, REQ-NFR-010
- Priority: High
- Created: 2026-11-12
- Model: deepseek-v4.1-flash:1017
- Branch: feature/feature-local-first-sync

## 目的

記録の入力を端末内の IndexedDB へ先に保存し、サーバーへの送信を入力の完了条件にしない。
再読み込みの後も記録の続きから再開でき、通信が復帰したら未送信の操作を自動で送る。
未保存の記録がある間は、その状態を画面に表示する。

## 優先度根拠

ジムの通信環境では、サーバーの応答を待つとセットの記録が止まる。
入力の保存と送信の順序を先に固定しないと、記録の機能ごとに保存の経路がばらける。

## 現状

0007 のアプリシェルと 0019 の種目の型があるが、記録の表、IndexedDB の保存、送信待ちの列、再読み込みの復元、同期の API がない。
そのため、入力のたびにサーバーへ送る実装になり、通信が切れると記録を続けられない。

## 設計方針

記録の入力は、IndexedDB の取引の中で、記録の実体と送信待ちの操作を同時に書く。
取引が成功した後に画面を更新する。
サーバーへの送信は、送信待ちの列の先頭から順に行う。
サーバーの応答を待たずに、次の入力を受け付ける。

IndexedDB のデータベースは版を持ち、スキーマを変えるときは移行する。
ADR-002 は、記録の入力を端末内の永続ストレージへ書いてから画面へ反映し、サーバーへの送信を入力の完了条件にしないと決めている。
ADR-020 は、IndexedDB の操作をアプリ本体の Rust から行うと決めている。
この issue はこれらの決定に従う。
移行に失敗した場合は、未同期の記録を保持したまま再試行できるようにする。
未同期の記録を保護するため、アプリはブラウザに永続ストレージの許可を求める。

IndexedDB の保存の対象は、トレーニング、トレーニングの種目、セット、ドロップセットの段、スーパーセットの組、送信待ちの操作、同期の状態を持つメタとする。
トレーニング、種目、セット、段、組の ID は、アプリが生成した UUID v4 とする。

送信待ちの操作は、操作 ID、トレーニング ID、列の中の順序、種別、本文、状態、試行回数、親の操作 ID を持つ。
状態は `pending`、`sending`、`blocked`、`failed` とする。
同じトレーニングの操作は順序を保つ。
依存する操作は、親の操作が解決するまで `blocked` とする。
親の操作が成功したら、依存する操作をまとめて送る。
親の操作を破棄した場合は、依存する操作も破棄する。
恒久的なエラーで失敗した操作は `failed` として列から外し、後続の操作を止めない。
画面に失敗を表示し、利用者が再試行か破棄を選べるようにする。

サーバーは `POST /api/sync/operations` で 1 つの操作を受け取る。
操作 ID を一意のキーとして保存し、同じ操作 ID の再送では状態を変えずに成功を返す。
操作の適用と操作 ID の保存を `batch()` でまとめる。
操作の形式と所有権を検証し、不正な操作を 400 で拒否する。
この issue では、トレーニングの作成と更新の操作だけを実装する。
ほかの操作の種別は、0022 以降の issue が登録する。

アプリは、起動時に IndexedDB から状態を復元する。
記録中のトレーニングがある場合は、記録画面を開く。
サーバーに保存済みの内容で、端末内の記録を上書きしない。
`clear_account` を提供し、IndexedDB と送信待ちの列を削除する。0063 が削除の応答の成功の後に呼ぶ。削除済みのアカウントの操作は再送せず、同じアカウントでログインしても削除の前の記録を復元しない。
通信が復帰したときと、アプリの起動時に、送信待ちの列を送る。
未保存の操作がある間は、画面に未保存の状態を表示する。

過去の記録を未接続で閲覧するためのキャッシュは持たない。
アプリが読み込まれた後は、未接続でも記録中のトレーニングを続けられる。

## 完了条件

- [ ] トレーニングの作成と更新の操作が、端末内の保存の後、サーバーの応答を待たずに画面へ反映される。セットの入力と完了は 0025 が同じ経路で確かめる。これは REQ-NFR-007 の受入基準に対応する。
- [ ] 通信を切った状態でも、記録の入力 (この issue ではトレーニングのメモ) を続けられ、入力した内容が失われない。セットの入力と完了は 0025 が確かめる。これは REQ-NFR-003 の受入基準に対応する。
- [ ] 通信が復帰している状態で記録中に再読み込みをすると、記録画面が開き、入力済みの内容 (この issue ではメモ) が残った状態から続けられる。タブを閉じて開き直した場合も同じ状態から再開できる。これは REQ-NFR-004 の受入基準に対応する。
- [ ] 通信が復帰すると、未送信の操作が自動でサーバーへ送られる。未保存の操作がある間は、その状態が画面に表示される。これは REQ-NFR-005 の受入基準に対応する。
- [ ] 同じ操作 ID の再送で、サーバーの状態が変わらない。
- [ ] 恒久的なエラーで失敗した操作が `failed` になり、後続の操作が止まらない。画面から再試行か破棄を選べる。
- [ ] 親の操作が `blocked` の間、依存する操作が送られない。親を破棄すると、依存する操作も破棄される。
- [ ] IndexedDB のスキーマの移行に失敗した場合、未同期の記録を保持したまま再試行できる。
- [ ] ブラウザが永続ストレージの許可を出さない場合も、記録の入力と画面の反映が続く。
- [ ] 記録中のトレーニングの作成と更新の操作が、サーバーの D1 に保存される。
- [ ] `clear_account` が IndexedDB と送信待ちの列を削除し、削除済みのアカウントの操作を再送しない。削除の後に同じアカウントでログインしても、削除の前の記録が復元されない。これは `REQ-NFR-010` の受入基準のうち、端末内の記録の削除と再ログイン後の復元の禁止に対応する。
- [ ] ブラウザのテストで、IndexedDB への保存、送信待ちの列の順序、失敗と再試行、移行を確かめる。
- [ ] E2E で、CDP のネットワークのエミュレーションで通信を切り、入力し、通信を戻して再読み込みし、復帰後の同期と未保存の表示を確かめる。
- [ ] Safari の E2E で、記録中に再読み込みすると記録画面が開き、入力済みのメモが残ることを確かめる。セットの入力と復元は 0025 が確かめる。これは `REQ-NFR-004` の受入基準のうち、再読み込みの後の復元に対応する。
- [ ] 結合テストで、同じ操作の再送が状態を変えないこと、操作の適用と操作 ID の保存が同じ `batch()` で行われることを確かめる。
- [ ] PBT で、送信待ちの列の状態遷移が、同じ操作の再送で結果を変えず、親の解決まで依存する操作を送らないことを確かめる。

## 解決方法

`migrations/` に `training_sessions`、`training_exercises`、`sets`、`set_segments`、`supersets`、`superset_members`、`applied_operations` の表を追加する。
`backend/warrior_core/src/sync.rs` に操作の型、状態遷移、順序の規則を置く。
`backend/warrior/src/sync.rs` に `POST /api/sync/operations` と操作の適用の登録を置く。
`frontend/src/storage/mod.rs`、`indexeddb.rs`、`outbox.rs` に IndexedDB の保存と送信待ちの列を置く。
`frontend/src/screens/record.rs` に記録の開始とメモの保存を置く。
`frontend/src/screens/home.rs` に記録中のトレーニングへ戻る遷移を置く。
`frontend/src/text.rs` に開始、メモ、同期の状態の文言を追加する。
`frontend/src/app.rs` に起動時の同期を置く。
`frontend/src/sync.rs` に、通信の復帰と起動のときに列を送る処理を置く。
`frontend/tests/storage.rs` にブラウザのテストを追加する。
`backend/warrior/tests/e2e_offline.rs` に E2E を追加する。
`backend/warrior/tests/e2e_safari_indexeddb.rs` に Safari の E2E を追加する。
`backend/pbt/tests/sync.rs` に状態遷移の性質テストを置く。
`backend/warrior_core/src/account_deletion.rs` の表の一覧に利用者に属する表を追加する。
