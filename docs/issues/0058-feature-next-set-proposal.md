# 次回セットの提案の生成と採用を実装する

- Requirements: REQ-AI-006, REQ-AI-007, REQ-AI-008, REQ-AI-009, REQ-AI-016, REQ-AI-018, REQ-GOAL-003
- Priority: Medium
- Created: 2026-11-12
- Model: deepseek-v4.1-flash:1017
- Branch: feature/feature-next-set-proposal

## 目的

種目ごとに、次回の推奨セットを提案し、保存する。
保存した提案を、次にその種目の記録を始めるときに入力欄の候補として表示し、1 回の操作で採用でき、自由に修正できるようにする。
提案には理由を 1 文で添え、痛みやけがの記述がある場合は負荷を増やす提案をしない。

## 優先度根拠

次回セットの提案は段階 3 の中心の機能であり、記録の入力の手間を減らす。
提案の保存と採用の形を先に固定しないと、記録の開始のたびに AI を呼ぶことになる。

## 現状

0014 で AI のコンテキストと出力の検証と安全ガード、0055 で生成の状態と Queue、0056 で日の評価を実装する。
しかし、次回セットの提案の生成、保存、候補の表示、採用、修正、理由の表示がない。

## 設計方針

次回セットの提案は、トレーニングの終了時に、記録のある種目ごとに生成する。
記録のない種目には提案を作らない。
提案は、利用者、種目、グリップとアタッチメントの組ごとに 1 件を最新として保存する。
同じ組の提案が既にある場合は、新しい提案で置き換える。

提案の入力は、前回のセット数、重量と回数、RPE、反動と補助の回数、種目に残したメモ、目標重量とする。
時間の種目では、前回の時間とセット数とする。
グリップとアタッチメントを選べる種目では、前回と同じものを使う前提で提案する。

提案は、種目、グリップとアタッチメント、重量、回数または時間、セット数、理由を持つ。
理由は 1 文とする。
重量を増やす幅は固定の上限で決めず、その種目の前回のセット数、回数、メモから AI が判断する。
前回、セットが進むにつれて回数が大きく落ちた場合や、反動や補助が多い場合は、重量を据え置く。

保存した提案は、次にその種目の記録を始めるときに入力欄の候補として表示する。
利用者が 1 回の操作で提案の値を入力欄に反映できる。
反映した後に自由に書き換えられる。
事前に提案を修正した場合は、修正後の内容を保存し、次回の記録では修正後の値を候補にする。
提案の一覧を開き、次回の記録を始めるまで、いつでも確認と修正ができる。

痛み、けが、体調不良の記述がある場合は、0014 の安全ガードで、その種目の負荷を増やす提案を除く。
負荷を下げるか休むことと、続く場合は医師などの専門家への相談を案内する文を表示する。

AI の生成に失敗した場合、または提案がない場合は、候補を表示せずに記録を続けられる。
記録の操作を止めない。

## 完了条件

- [ ] 種目ごとに、重量、回数、セット数の提案が表示される。時間で記録する種目では、時間とセット数の提案が表示される。これは REQ-AI-006 の受入基準に対応する。
- [ ] 種目の記録を始めると、保存した提案が入力欄の候補として表示される。1 回の操作で提案の値を入力欄に反映でき、反映した後に自由に書き換えられる。事前に修正した提案は、修正後の値が候補になる。これは REQ-AI-007 の受入基準に対応する。
- [ ] 各提案に、理由が 1 文で添えられる。これは REQ-AI-008 の受入基準に対応する。
- [ ] 重量を増やす提案の幅に固定の上限を設けない。同じ種目でも、前回のセット数、回数、メモが違えば、提案する増加の幅が変わる。これは REQ-AI-009 の受入基準に対応する。
- [ ] トレーニングを終了すると、記録のある種目ごとに次回セットの提案が保存される。保存した提案は、次回のその種目の記録を始めるまで、いつでも開いて修正できる。記録のない種目には提案が作られない。これは REQ-AI-018 の受入基準に対応する。
- [ ] 目標重量を設定した種目では、次回セットの提案が目標重量を踏まえた内容になる。これは REQ-GOAL-003 の受入基準に対応する。
- [ ] 提案が、利用者、種目、グリップとアタッチメントの組ごとに 1 件を最新として保存される。
- [ ] 痛み、けが、体調不良の記述がある場合、その種目の負荷を増やす提案が表示されない。代わりに負荷を下げるか休むことと、専門家への相談を案内する文が表示される。これは REQ-AI-016 の受入基準に対応する。
- [ ] 提案の入力に、前回のセット数、重量と回数、RPE、反動と補助の回数、種目のメモ、目標重量が含まれる。
- [ ] 固定の AI の出力を使って、重量と回数、時間の種目、グリップの分離、理由、採用、修正、記録のない種目、痛みの記述を確かめる。
- [ ] PBT で、提案の採用と修正の後に、次回の候補が保存された値と一致することを確かめる。
- [ ] PBT で、同じ種目とグリップの組の提案が 1 件だけ保存され、新しい提案で置き換わることを確かめる。
- [ ] 例示テストで、前回のセット数と回数とメモが違う 2 つの入力に対して、提案の増加の幅が変わることを確かめる。AI の出力は固定の 2 つの例を使う。
- [ ] E2E で、固定の `ai_outputs` を投入し、提案を表示し、1 回の操作で採用し、書き換え、次回の記録で修正後の値が候補になることを確かめる。

## 解決方法

`backend/warrior_core/src/proposal.rs` に、提案の型、一意キー、採用と修正の規則、痛みの記述がある場合の扱いを置く。
`backend/warrior/src/proposal.rs` に、提案の取得、保存、修正を置く。
`backend/warrior/src/router.rs` に `GET /api/proposals`、`PUT /api/proposals/:id` を追加する。
`backend/warrior/src/training_session.rs` の終了の処理で、種目ごとの提案の生成の行を作る。
`frontend/src/screens/record.rs` に提案の候補、採用、修正を置く。
`frontend/src/screens/exercise.rs` に提案の一覧と修正を置く。
`frontend/src/text.rs` に提案の理由と安全の案内の文言を追加する。
`backend/warrior/tests/e2e_next_set_proposal.rs` に E2E を追加する。
`backend/pbt/tests/proposal.rs` に性質テストを置く。
実モデルの品質は 0069 で確認する。
