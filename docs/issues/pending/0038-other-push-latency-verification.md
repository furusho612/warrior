# プッシュ通知の遅延を実機で計測し、採用を決める

- Requirements: REQ-TMR-012
- Priority: High
- Created: 2026-11-12
- Model: deepseek-v4.1-flash:1017
- Branch: feature/other-push-latency-verification

## 目的

プッシュ通知の試作を iPhone と Android の実機で動かし、レスト終了から通知が届くまでの遅れを測る。
合格の基準を満たすかどうかを決め、満たさない場合はプッシュ通知を補助の位置づけに変える。

## 優先度根拠

PRD はプッシュ通知の試作を段階 1 のうちに行い、採用するかを先に決めると定める。
合格しなければ、主な手段を画面の消灯防止と音に変える必要がある。

## 現状

0036 でプッシュ購読と Service Worker の通知表示、0066 でサーバーの予約、送信時刻と受信時刻の記録、`mise run verify-staging` の集計を実装する。
しかし、0067 で staging を追加してデプロイした実機での計測と、採用の判断がまだない。

## 設計方針

0067 で staging を追加してデプロイしたアプリを、iPhone の Safari と Android の Chrome の実機で動かす。
iPhone ではホーム画面に追加し、通知を許可する。
各端末でレストを 10 回終了させ、レストの終了から通知が届くまでの時間を測る。
計測は `mise run verify-staging` を使い、サーバーの送信時刻と Service Worker の受信時刻の差を集計する。

合格の基準は、レスト終了から 5 秒以内に届く割合が 10 回中 9 回以上とする。
合格した場合は、プッシュ通知を主な手段の 1 つとして残す。
合格しない場合は、プッシュ通知を補助の位置づけに変え、主な手段を画面の消灯防止と音にする。
判断の結果を ADR-008 に追記するか、新しい ADR を起こす。

計測の結果は、端末の種類、OS の版、通知の許可の状態、試行の回数、5 秒以内に届いた回数、遅れの中央値と最大値を記録する。
個人の環境に依存する情報は、issue に書く。秘密の値は書かない。

## 完了条件

- [ ] iPhone と Android の実機で、0067 で staging を追加した後のアプリのプッシュ通知を 10 回ずつ動かし、レスト終了から通知までの時間を記録する。これは REQ-TMR-012 の受入基準に対応する。
- [ ] 各端末で、5 秒以内に届いた回数が 10 回中何回かを記録する。
- [ ] 10 回中 9 回以上の場合、プッシュ通知を主な手段の 1 つとして残す決定を ADR に記録する。
- [ ] 10 回中 9 回未満の場合、プッシュ通知を補助の位置づけに変え、主な手段を画面の消灯防止と音にする決定を ADR に記録する。
- [ ] 決定に合わせて、PRD の REQ-TMR-012 の扱いと、ADR-008 の記述を同じ変更で更新する。
- [ ] 計測の結果に、端末の種類、OS の版、通知の許可の状態、試行の回数、5 秒以内の回数、遅れの中央値と最大値を残す。

## 解決方法

`mise run verify-staging` を、0067 で追加した staging の URL に対して実行する。
iPhone の Safari でホーム画面に追加し、通知を許可する。
Android の Chrome で通知を許可する。
各端末で 10 回のレストを終了し、結果を issue に追記する。
結果に応じて ADR-008 または新しい ADR を更新し、PRD の REQ-TMR-012 の扱いを揃える。

## 止める理由

0067 の staging へのデプロイ、iPhone と Android の実機、通知の許可が利用者に依存する。
エージェントは実環境と実機に接続しない。

## 再開条件

利用者が 0003 の production を用意し、0067 で staging を追加してデプロイする。
iPhone と Android の実機で通知を許可し、10 回の計測を行う。
