# レスト終了のプッシュ通知をサーバーで予約する

- Requirements: REQ-TMR-009, REQ-TMR-010, REQ-TMR-011, REQ-TMR-012
- Priority: High
- Created: 2026-11-12
- Model: deepseek-v4.1-flash:1017
- Branch: feature/feature-rest-push-reservation

## 目的

セットの完了時に、サーバーがレストの終了予定時刻を決め、その時刻にプッシュ通知を予約する。
延長、短縮、スキップ、トレーニングの終了で予約を取り消すか時刻を変更し、通知は緊急度を最高にし、有効期限を短くし、遅れた通知を破棄する。
通信できない状態でセットを完了した場合は音と画面表示だけで知らせ、遅延の計測に使う終了予定時刻、送信時刻、受信時刻を記録する。

## 優先度根拠

プッシュ通知は段階 1 で試作し、実機の遅延を測って採用を決める。
予約と取り消しの状態をサーバーに持たせないと、古い通知の配信と二重の通知を防げない。

## 現状

0036 でプッシュ購読と Service Worker の通知表示、0037 で Web Push の送信を実装する。
しかし、レストの終了予定時刻の予約、Queue による遅延、取り消し、再予約、有効期限、遅延の計測がない。

## 設計方針

セットの完了時に、アプリはサーバーへレストの残り時間を送る。
0037 の次に、0038 の前に着手する。
サーバーは受け取った時刻から終了予定時刻を決め、`rest_push_reservations` の行を作る。
予約は、予約 ID、利用者 ID、トレーニング ID、端末の ID、版、終了予定時刻、有効かどうか、送信時刻、受信時刻を持つ。

サーバーは、予約 ID と版を持つメッセージを `JOBS_QUEUE` に送る。
メッセージの遅延は、終了予定時刻までの秒数とする。
メッセージには予約 ID と版だけを入れ、記録の本文を入れない。

延長と短縮では、版を進め、古い予約を無効にして、新しい終了予定時刻で予約し直す。
スキップとトレーニングの終了では、版を進めて古い予約を無効にし、新しい予約を作らない。
古い版のメッセージが届いても、通知を送らない。

消費側は、予約の行を読み、次の条件を全て満たす場合だけ 0037 の Web Push の送信を呼ぶ。

- 予約が有効である。
- メッセージの版が予約の版と一致する。
- 現在時刻が終了予定時刻以上である。
- 現在時刻が終了予定時刻から 30 秒以下である。
- まだ送信していない。
- 利用者と端末の行が D1 にある。

条件を満たさない場合は、メッセージを消費して終了する。
通知を送ったら、送信時刻を保存する。
同じメッセージを複数回処理しても、通知は最大 1 回とする。

送信の `Urgency` は `high` とし、`TTL` は `max(0, 30 - (現在時刻 - 終了予定時刻))` 秒とする。
終了予定時刻から 30 秒を過ぎたメッセージは送らない。

通知の宛先は、トレーニングを開始した端末の購読に限る。
同じアカウントのほかの端末には送らない。
通知の本文には、種目名、重量、回数などの記録の内容を含めない。

通信できない状態でセットを完了した場合は、アプリは予約を送らない。
音と画面表示だけでレストの終了を知らせる。
接続が戻った後に、過ぎたレストの予約を送らない。

遅延の計測のため、サーバーは送信時刻を保存する。
Service Worker は通知を受け取った時刻を `POST /api/push/received` に送り、サーバーは予約 ID と版に紐づけて受信時刻を保存する。
`mise run verify-staging` は、10 回のレスト終了時刻と受信時刻の差を集計し、5 秒以内が 9 回以上かを判定する。通知が届かなかった試行も失敗として数える。

Cron Triggers で、期限を過ぎた予約と、lease の期限を過ぎた Queue のジョブを回復する。

## 完了条件

- [ ] レスト終了のプッシュ通知が、緊急度を最高にして送られる。有効期限は終了予定時刻から 30 秒を上限とし、それを過ぎてから端末に届いた通知は、音も表示も出さずに捨てる。これは REQ-TMR-009 の受入基準に対応する。
- [ ] レストを途中で切り上げたときと、トレーニングを終了したときは、予約済みのプッシュ通知が届かない。レストを延長または短縮したときは、変更後の終了予定時刻にだけ通知が届く。これは REQ-TMR-010 の受入基準に対応する。
- [ ] 通信できない状態でセットを完了すると、プッシュ通知は予約されず、レストの終了を音と画面表示だけで知らせる。これは REQ-TMR-011 の受入基準に対応する。
- [ ] 通知が、トレーニングを開始した端末の購読にだけ送られる。同じアカウントのほかの端末には送られない。
- [ ] 同じ予約 ID と版のメッセージを複数回処理しても、通知が最大 1 回である。
- [ ] 古い版のメッセージが届いても、通知を送らない。
- [ ] 終了予定時刻から 30 秒を過ぎたメッセージを送らない。
- [ ] Queue のメッセージに予約 ID と版だけが入り、記録の本文が入らない。
- [ ] 予約の作成、延長、短縮、スキップ、終了が、0010 の TLA+ のモデルの遷移と対応する。
- [ ] サーバーがレスト終了時刻と送信時刻を、Service Worker が受信時刻を保存し、`mise run verify-staging` が 10 回のレスト終了時刻と受信時刻の差を集計して 5 秒以内が 9 回以上かを判定する。通知が届かなかった試行も失敗として数える。これは REQ-TMR-012 の受入基準のうち、計測の部分に対応する。採用の判断は 0038 が担う。
- [ ] ローカルの `wrangler dev` の Queues で、予約の作成、取り消し、再予約、古いメッセージの無視を確かめる。
- [ ] PBT で、送信の条件が、予約の有効性、版、時刻の範囲、送信済みの 4 つの条件の全てを満たす場合だけ真になることを確かめる。
- [ ] 例示テストで、終了予定時刻の 1 秒前、ちょうど、30 秒後、31 秒後、古い版、送信済みを確かめる。
- [ ] E2E で、CDP の `ServiceWorker.deliverPushMessage` を使い、通知の表示と、押したときの画面の移動を確かめる。実際の配信は staging の実機で 0038 が確かめる。

## 解決方法

`migrations/` に `rest_push_reservations` の表を追加し、`push_subscriptions` に端末の ID を追加する。
`backend/warrior_core/src/rest_push.rs` に、送信の条件と予約の版の規則を置く。
`backend/warrior/src/push.rs` に、予約の作成、取り消し、再予約、消費側の処理を置く。
`backend/warrior/src/queue.rs` に、`JOBS_QUEUE` の producer と consumer を置く。
`backend/warrior/src/scheduled.rs` に、期限を過ぎた予約と lease の回復を追加する。
`backend/warrior/src/router.rs` に `POST /api/rest/reservations`、`PATCH /api/rest/reservations/:id`、`DELETE /api/rest/reservations/:id`、`POST /api/push/received` を追加する。
`frontend/src/screens/record.rs` のセットの完了とタイマーの操作から予約を呼ぶ。
`mise.toml` に `verify-staging` を追加する。
`backend/warrior/tests/rest_push.rs` に結合テストを追加する。
`backend/pbt/tests/rest_push.rs` に性質テストを置く。
`backend/warrior_core/src/web_push.rs` の送信の関数を呼ぶ。
